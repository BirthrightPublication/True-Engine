# TRUE ENGINE engineering contract

Stay within the approved 0.1 foundation line, including the explicitly requested 0.1.1 delivery patch, until the owner approves a future feature phase. Preserve existing public APIs and schema compatibility; breaking changes require explicit approval. Keep the engine application-agnostic: license plate logic belongs in a consumer application.

Use the existing isolated checkout, without creating a worktree unless requested. Read docs/SDK-0.1.md before changing public behavior. Prefer small modules, retained GPU resources, and event-driven rendering. Never claim platform execution or performance measurements without evidence.

Before delivery run `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `EGL_PLATFORM=surfaceless cargo test --workspace --locked`, and `python3 -m unittest discover -s tools -v`. The GPU test requires EGL/OpenGL and asserts rendered pixels. Preserve failures and skipped checks in release notes. Run wasm and Windows target checks where available; build and run Windows releases on Windows before marking them verified.

Every release/patch must include changed files, actual test commands/results, SDK/schema compatibility, migration behavior, package and payload SHA-256. Keep user projects under Data, outside replaceable Current. Never invent test results, disable integrity verification, or push/publish a release without authorization. No future phases without approval.

The permanent roadmap and continuation policy are in [docs/ROADMAP.md](docs/ROADMAP.md). Treat an owner message saying “Continue” as an instruction to implement the next practical milestone or patch in the approved phase. Explicit approval is still required to begin a future release phase. Coordinate consumer integration through the versioned SDK; do not edit consuming application repositories. Keep existing picking, hierarchy, serialization, and SDK APIs compatible even though the roadmap schedules their broader systems for later phases. Do not build expensive generalized systems without demonstrated application need.

Read [docs/PERMANENT_DEVELOPMENT_DIRECTIVE.md](docs/PERMANENT_DEVELOPMENT_DIRECTIVE.md) for the owner's release and continuity requirements. On continuation, read NEXT_ITERATION.md first and reconcile it with actual code and evidence. The active priority is making the existing v0.1.0 Windows test release installable and testable; do not add engine features until that baseline is tested. Keep the engine and License Plate Obfuscation Studio in separate repositories/installations. Maintain local version tags for delivered versions; do not push without authorization.

Follow [docs/GITHUB_REPOSITORY_RULES.md](docs/GITHUB_REPOSITORY_RULES.md). `BirthrightPublication/True-Engine` is the authoritative GitHub source. Fetch and inspect before development, preserve unrelated work, use a dedicated feature branch, commit/push approved iteration work, open PRs where supported, merge only approved changes, verify remote refs, and keep release tags immutable. Record source-to-package hashes under releases/. Report blocked PR/API/asset operations honestly. The owner's standing repository workflow authorizes these routine pushes; never force-push stable history or mix project repositories.

Do not select an open-source license or commercial terms for the owner's original code. Read LICENSING.md and docs/PUBLICATION_REVIEW.md before public binary distribution. Preserve original third-party license expressions; inventory metadata is not legal clearance or a shipped-binary SBOM. Exclude secrets/private state and review publication contents. Commercial/public binary release requires applicable dependency notices and the owner's licensing decision; source visibility alone is not an open-source grant. Keep API compatibility and migrations explicit for version-pinned consumers.

Standard releases use tools/release/package.py and .github/workflows/windows-release.yml; never move old tags or clobber release assets. The Windows updater replaces only managed app/, retains Build/root/legacy/persistent data, and refuses incompatible or conflicting state. Run its integration suite and packaging tests when modifying delivery code. GitHub Windows CI and live publication must be verified independently of local Linux checks; do not call a release uploaded merely because a tag push succeeded.

The owner explicitly approved the additive browser SDK integration task after the verified 0.1.2 release. Version 0.1.3 adds a host-owned WASM canvas SDK using the existing renderer and external indexed meshes; it does not authorize unrelated roadmap phases or consumer repository edits. Read docs/BROWSER_SDK_API.md and docs/PLATE_STUDIO_INTEGRATION.md. For SDK changes also run the document/custom-mesh tests, tools/sdk unit tests, staged SDK TypeScript checks and actual packaged browser example pixel/input/file round-trip tests. Preserve the separate browser envelope and native schema 1.
